# Audit, September 2026

An adversarial read of the code and the documentation, done on `main` at `c73d486` (2026-09-24) on Linux
(Python 3.11, PyYAML 6.0.1 without libyaml, numpy 2.4, the distribution's libopenmpt 0.7.3, node 22). Line numbers
below refer to that commit; the fixes on this branch (`audit/2026-09`) moved a few of them. Every finding says whether
it was **confirmed** (reproduced here, with the steps) or only **suspected** (from reading), and whether this branch
fixes it. Nothing in `suite/` was touched, and nothing from the Unreal Tournament modules was used or added.

## Findings, by severity

Severity: **high** loses or corrupts the user's data; **medium** breaks a documented use or lets a file the user did
not write run code or exhaust memory; **low** a crash, a dead request or a wrong detail with a workaround.

### 1. Data loss and silent corruption

**F1. U (apply) and WRITE MIX (apply_mix) wrote the song file unchecked: a change made on disk was overwritten, a
broken song could be written, and neither was an undo step.** High. Confirmed. **Fixed** (`9e04ba0`).
`vulturetracker/gui.py:1272-1289`. Every other write goes through `_commit` (a `dirty()` refusal, a whole-song
compile, one history entry); these two called `write_song` directly.
- Reproduction (overwrite): open a song, move a fader, edit `title:` in the YAML by hand (or rerun the generator),
  then WRITE MIX. Observed: the hand edit is gone from the file; `dirty()` was true and nothing refused the write. The
  same for U with a candidate. Test: `test_apply_and_write_mix_are_checked_and_undoable`.
- Reproduction (broken song): a candidate WAV whose `smpl` unity note is 125 (`write_wav(..., root_note=125)`), U.
  Observed: `1: {file: hi.wav, name: hi, base_note: ~~~}` written; the song no longer compiles; no undo.
- Reproduction (undo): after U or WRITE MIX, `snapshot()["undo"]` is unchanged; Ctrl+Z steps over the write to the
  edit before it.
- Fix applied: both compile first, refuse when the file changed on disk, and commit as one undo step; the tryout
  meta changes (the candidate list, the mix) still happen only when the write goes through. The README's claim that
  every change is compiled first and undoable is true now.

**F2. Zero-padded slot numbers (`08:`, `09:`) compile but the app read them as strings: a GAIN written for the slot
was dropped silently, the slot could not be shown or edited, and a stale tryout slot made the song unopenable.**
Medium. Confirmed. **Fixed** (`d7aabbd`). `gui.py:730` (`api.from_yaml`), `:735` (`min()` over the keys),
`:1226` (`mix_text`), `:1845` (`_sample_wav`); the compiler's `_numbered` (`song.py:195`) accepts any digit string, and
`song._convert` reads `08` as decimal on purpose.
- Reproduction: `samples: {1: {...}, 08: {...}}` (a natural spelling for a tracker person; `01`..`07` are octal-valid
  and read as ints, `08` and `09` as strings). `check` passes. In the app: GAIN 40 on slot 8, WRITE MIX: the diff shows
  no change and the mix is cleared, the value is gone. SAMPLES tab on slot 8: "sample slot 8 has no WAV". With
  `{"slot": 3}` in `<song>.tryout.json`: `State()` raises `TypeError: '<' not supported between 'str' and 'int'`.
- Fix applied: `reload` turns digit-string keys of `samples` and `instruments` into ints (the line-based writer already
  matched `08:` lines by number). Test: `test_zero_padded_slot_numbers`.

**F3. Undo does not undo the tryout's remap of mutes and faders after a channel is removed or moved.** Medium.
Confirmed. Not fixed (report). `gui.py:1816-1831`: after `_commit`, `song_edit` remaps `meta["muted"]`, `meta["solo"]`
and the mix's `volume`/`pan` keys to the new channel numbers; `undo` (`:1832`) restores the text only.
- Reproduction: three channels, mute channel 3 and set its fader to 10; remove channel 2; Ctrl+Z. Observed: the song
  has three channels again, but `muted == [1]` and the fader sits on channel 2 (index 1): the mute and the level are
  now on the wrong channel, and the next render is silently wrong.
- Suggested fix: keep the meta before each remap on the history stack beside the text (or store the inverse remap)
  and restore it in `undo`/redo; or clear mutes and faders when a structure edit is undone and say so.

**F4. A tryout section that contains a `Bxx` jump to an order outside it cannot be compiled, so every candidate
render of that section fails.** Medium. Confirmed. Not fixed. `api.py:179` (`tryout_song` slices the order list),
`song.py:_check_pattern_refs` ("Bxx jumps to order N but the order list has M entries" is an error).
- Reproduction: `demo/arena.yaml` and `demo2/iron_relay.yaml` end with `B01` (the documented loop idiom); pick a
  section of one order that includes the last pattern. Observed: every candidate shows RENDER FAILED with
  `SongError: ... B01 jumps to order 1 but the order list has 1 entries`; the live engine, which plays the whole song,
  is unaffected.
- Suggested fix: in `tryout_song`, drop (or turn into `B00`-to-self, i.e. clear) any `Bxx` whose target falls outside
  the slice, in the copy only; or make the check a warning when compiling a tryout copy.

**F5. A block-style order list is rewritten on one line and the comments inside it are lost, without warning.** Medium
(comments are the user's notes). Confirmed. Not fixed. `gui.py:1808-1811`: when `orders:` is not a one-line flow list,
`lines[i:_span]` is replaced by the one-line form. GUIDE.md:158 says such a layout is "refused with the reason".
- Reproduction: `orders:\n  - p1  # intro\n  # the drop\n  - p2\n`, then any order edit in the SONG tab. Observed:
  `orders: [p2, p1]`; both comments gone; no diff shown (the SONG tab shows none).
- Suggested fix: refuse as documented, or keep the block layout (one `- name` per line, comments kept where the
  entry survives).

**F6. Every render is cut at ten minutes, silently.** Low-medium. Confirmed (mechanism). Not fixed.
`openmpt.py:149,169`: `LoadedModule.render(max_seconds=600)` stops reading at `mix_rate * 600` frames; `api.render`
(`api.py:143`), `_build`, the stems and encoded exports and the tryout all use the default.
- Reproduction: `render(RATE, oversample=1, max_seconds=0.5)` on a 1.06 s song returns 0.56 s (the cap rounds up to the
  4096-frame chunk); a 12-minute song exported as WAV/MP3 is 10 minutes long with no message. Not documented anywhere.
- Suggested fix: pass the cap through `api.render` (default to the song's own duration plus the repeats, keep a
  generous safety cap for endless loops) and say so in GUIDE.md.

**F7. The tryout meta, the notes and the song itself are written by truncate-then-write; a corrupt meta or notes file
blocks opening the song.** Low. Confirmed by reading. Not fixed. `gui.py:688-691` (`json.loads` in `__init__`),
`:748` (`save_meta`), `:1070` (`save_notes`), `:751` (`write_song`).
- What goes wrong: a crash or power loss mid-write leaves a truncated `<song>.tryout.json` or `.notes.json`;
  `State()` then raises `JSONDecodeError` (the CLI shows a traceback, the app's open a 400) until the file is removed
  by hand. A truncated song file loses the song (the undo history lives in memory only).
- Suggested fix: write to `<name>.tmp` in the same directory and `os.replace`; on a meta/notes file that does not
  parse, rename it to `.corrupt` and start fresh with a warning in the snapshot.

**F8. A UTF-8 BOM directly before `module:` makes the mixer re-dump the whole file and the SONG tab refuse module
edits.** Low. Confirmed. Not fixed. `gui.py:1170-1200` (`_edit_text` finds sections by `line.split(":")[0]`),
`:1477` (`_top` matches `^module\s*:`).
- Reproduction: a song saved with a BOM (older Notepad), `module:` as the first line. `check` passes (PyYAML skips
  the BOM). WRITE MIX: `redump` is true (comments would be lost; the diff modal does warn); `tempo` in the SONG tab:
  "the song has no top-level 'module:'". A BOM before a leading comment line is harmless.
- Suggested fix: strip `﻿` from `self.text` in `reload` and write it back in `write_song`.

**F9. The report of archived notes is rendered against the current song's orders, not the version the notes were
made on.** Low. Confirmed by reading. Not fixed. `gui.py:1074-1092` calls `self.report(kept, old_version)`, and
`report` (`:1093`) takes order names and times from `self.facts`, i.e. the new song. The archive's header carries the
old hash, its `## ord N` lines the new song's pattern names.
- Suggested fix: keep the order table (pattern name, start, seconds) in each note when it is made, and render the
  archive from that.

**F10. Opening a path that does not exist left a `.tryout` directory beside it.** Low. Confirmed. **Fixed**
(`d7aabbd`). `gui.py:684`: the cache directory was made before the song was read.

**F11. A sample or instrument entry written as a multi-line flow mapping crashed `sample_set`/`instrument_set` with
`AttributeError` (a dead request, no message).** Low. Confirmed. **Fixed** (`d7aabbd`). `gui.py:1714`, `:1753`:
`ENTRY` does not match `  2: {file: b.wav,` and `m` was used unchecked. Now refused with "written across several
lines".

**F12. `_redump`'s in-place substitution can land in a trailing comment.** Low. Suspected (constructed, not seen in a
real song). Not fixed. `gui.py:1146-1160` with `ENTRY`'s greedy `(\{.*\})`: a line like `- {name: A}  # pan: 40 }`
makes the flow group include the comment; a mixer write of `pan` then substitutes inside the comment (`re.subn` finds
one match), the real value is never written, and WRITE MIX clears the fader: the level is lost silently.
- Suggested fix: match the flow mapping non-greedily up to the first `}` at bracket depth zero, or re-dump the entry
  when the substituted key is not found in the parsed entry.

Also noted, not bugs by themselves: `write_song` turns mixed line endings into all-CRLF (documented as "the file's own
endings"); a song using YAML anchors or merge keys loses them on the re-dump path; `_yname` cannot express a title
that contains ` #` inside quotes (the module op is refused by the compile check, not corrupted).

### 2. Security of the local server and the page

**S1. Script injection from a song file: names and fields reached inline handlers with only the double quote
escaped, so a name containing the text `&quot;` ran as script when clicked.** Medium. Confirmed in Chromium.
**Fixed** (`b5d211a`). `vulturetracker/gui.html:364, 730, 738, 826, 827, 885, 892, 898, 900` (every
`JSON.stringify(x).replace(/"/g,'&quot;')` and the `&#39;` variant in `renderClean`), and `:473` (`M.error` raw in a
`title` attribute).
- Why: an attribute value is HTML first and JavaScript second. `onclick="typeIn(this,0,0,...,&quot;x&quot;);alert(7);//&quot;)"`
  decodes to `"x");alert(7);//"` before the handler is parsed. `esc()` was applied to the text nodes but not to the
  JSON inside the handlers, and `JSON.stringify` does not escape `&`.
- Reproduction: `module: {title: 'x&quot;);alert(7);//'}` (19 ASCII characters: a legal title) and a channel
  `{name: 'c&quot;);alert(8);//'}`; the song compiles. SONG tab, click the title or the channel name to type it.
  Observed (Playwright, headless Chromium): `alert(7)` and `alert(8)` fire. Pattern names in the CLEAN-UP list and
  sample and instrument fields in their tabs go the same way. What such a script can do: everything the page can,
  as the page (the Origin check passes): create song files at any path (`/api/new`), write WAVs beside the song,
  import a module beside any file, rewrite the song. So a song file someone downloads and opens is a code path into
  the file system, on a click.
- Fix applied: `attr(x)` = `esc(JSON.stringify(x))` with `'` as `&#39;`; every handler value goes through it; the
  meters' error text is escaped. `tests/test_page.py` checks the markup statically and, with Playwright installed,
  drives the real page (skipped otherwise).

**S2. A request body an action cannot use dropped the connection instead of answering.** Low. Confirmed. **Fixed**
(`856e5be`). `gui.py:2141` (`json.loads` outside the `try`), `:2210` (`TypeError`/`AttributeError` not caught),
`:2114` (`/api/diff/N` unguarded). `{"slot": []}`, a body that is not JSON, `/api/diff/7` with no such candidate:
the handler thread died with a traceback and the page's `fetch` failed without a status. Local only, but a page
stuck on "writing…" is the symptom.

**S3. `_send_file` trusts the Range header.** Low. Confirmed. Not fixed. `gui.py:2027-2047`: `bytes=0-999999999`
answers 206 with `Content-Length: 1000000000` and 100 KB of body (the client waits for the rest; urllib raises
`IncompleteRead`); `bytes=abc-` raises `ValueError` and kills the request thread. Chromium's `<audio>` sends
`bytes=N-` only, so the app's own player is fine.
- Suggested fix: clamp `end` to `len(data) - 1`, answer 416 for a start past the end, and catch `ValueError`.

**S4. What was checked and holds.** The `Origin`/`Host` refusal (`_foreign`, `gui.py:2049`) covers every route:
POSTs from another page carry an `Origin` and are refused, `Origin: null` is refused, a DNS-rebinding page fails
the `Host` check, and the page's own requests (127.0.0.1 or localhost with the server's port) pass. No GET has a
side effect. `/wav/` and `/spec/` serve only files the server rendered (keys from `renders`), `/raw/` only WAVs the
user added as candidates, `/api/wave/` only the slot's own file. Uploads are named from a sanitised stem beside the
song and never replace another file; `_new_wav` and `import_beside` number their outputs. `open`, `new`, `import`
and `sample_new` take any absolute path: that is the local user's own request, and the Origin check is what stands
between a web page and them. Residual, accepted: any process on the machine can drive the server (no token), as with
every localhost app of this kind. `typeIn` assigns `.value`, never markup. Every other name reaching markup goes
through `esc()`.

**S5. Each open leaks the previous `State`'s worker thread.** Low. Suspected. `gui.py:1994` (`open_song` replaces the
class attribute); `_worker` (`:940`) loops on its queue forever and keeps rendering into the old song's `.tryout/`,
pruning it (`_prune`, `:989`) against the new state's writes when the same song is reopened.

### 3. Parsing untrusted files

**P1. An IT or XM file claiming 65535 rows in a pattern was allocated as a grid of 4 million `Cell` objects.**
Medium. Confirmed. **Fixed** (`9021053`). `itreader.py:227-229`, `modreader.py:375`.
- Reproduction: patch the row count of a compiled IT's first pattern to 65535 (two bytes), `read_it`. Observed:
  5.3 s and +556 MB resident for one pattern; a file with 256 such patterns would take the machine down. libopenmpt
  drops a pattern with more than 1024 rows (measured: 1024 loads, 1025 reports 0 rows).
- Fix applied: rows outside 1..1024 leave the pattern empty with a warning (the same as a zero pattern pointer).

**P2. Truncated or garbled S3M, XM and IT files let `struct.error`, `IndexError` and `ValueError` escape the
readers.** Medium. Confirmed. **Fixed** (`9021053`). `modreader.py:229` (`insptr = struct.unpack_from`), `:300`
(`data[i + 1]`), `:335-337` (six-byte unpack), `:365-377` (XM headers), `itreader.py:159` (pointer tables), `:241`
(`pd[i]`). Truncating the test writers' modules at every length: S3M 9 escapes of 249 lengths, XM 270 of 348, IT 29
of 7619; MOD none. The CLI's `import` catches only `OSError` and `ValueError` (`__main__.py:170`), so these were
tracebacks; the app's IMPORT A MODULE dropped the request.
- Fix applied: `read_module` wraps them in `ModReadError` (the IT reader's own `ITReadError` passes through).
  Test: `test_malformed_files_are_read_errors`.

**P3. `read_wav` divided by zero or let `struct.error` out on a header it could not use.** Medium (the snapshot
reaches it). Confirmed. **Fixed** (`d68a464`). `wavload.py:51-56`: `nch == 0` or `align == 0` or `align < nch`
(width 0) gave `ZeroDivisionError`; a `fmt` chunk shorter than 16 bytes gave `struct.error`; `rate == 0` loaded and
divided later in `measure`. Neither is a `WavError`, so `song._sample` did not turn it into a line error, `check`
printed a traceback, and a candidate WAV like this made every `/api/state` fail (the measurement runs inside
`snapshot`).

**P4. YAML that nests without end, or an alias inside its own anchor, was a `RecursionError`.** Low. Confirmed.
**Fixed** (`9021053`). `song.py:53` (`_convert`), `:789`, and PyYAML's pure-Python parser itself. Now a `SongError`
("the YAML nests too deeply, or an alias refers to its own anchor").

**P5. An IT with patterns of 201 to 1024 rows imports to a song that does not compile.** Low. Confirmed by reading.
Not fixed. `itreader.py:module_to_song` writes `rows: 300`; the format allows 200. XM patterns are split into
192-row parts (`modreader._split_long`), IT patterns are not (only `read_xm` calls it), although libopenmpt plays
them.
- Suggested fix: call `_split_long` from `read_it` too (it needs the `_Warn` helper or a plain list).

**P6. An IT whose cells or keymaps name sample or instrument numbers above 99 imports to a song with keys above 99.**
Low. Suspected (constructed). Not fixed. `itreader.py:400-410`: `module_to_song` pads `mod.samples`/`mod.instruments`
up to the highest number used, and `_numbered` then rejects the keys. libopenmpt ignores such references.
- Suggested fix: drop references above 99 with a warning, as `_sanitize` does for effects.

**P7. Observation.** `_decompress` (`itreader.py:25`) is a pure-Python bit reader: a large IT 2.14-compressed sample
takes seconds per megasample. Not measured here (no compressed fixture in the repository).

Conversion fidelity: `tests/test_modimport.py` pins the MOD, S3M and XM mappings to libopenmpt renders (mean level
within 0.5 dB, pitch within cents) over a matrix of effects; the mappings were read against the formats (ProTracker
E-commands, XM's volume column and key-off rules, S3M's shared memory and pan table) and are consistent with it. No
real-world module is in the repository, so the GUIDE's numbers over 33 files could not be re-measured.

### 4. The live engine

**E1. A `load` that fails inside the worklet hangs the page's engine state.** Low. Suspected. Not fixed.
`engine-worklet.js:59-70` posts `{type:'error'}` and never `loaded`; `gui.html:575-577` (`lvLoad`) awaits
`LV.onLoaded`, which then never resolves: `LV.loading` stays true (no further swap is ever attempted, the engine keeps
playing the old song while the status says "swapping the song in…"), and when it was the first load (`lvStart`,
`:568`) `LV.ready` never settles, so ▶ does nothing for the rest of the session. Triggering it needs a module the
wasm build rejects (the server does not verify `/api/it` with the DLL; `build` does), e.g. one larger than the wasm
heap.
- Suggested fix: reject the pending load promise on an `error` message (carry an id in `load`/`loaded`/`error`).

**E2. Two loads in flight overwrite `LV.onLoaded`.** Low. Suspected. `gui.html:568-586`: `lvSync` starts `lvLoad(true)`
when the key changes while `lvStart`'s `lvLoad(false)` still awaits its `loaded`; the first promise never resolves and
`LV.ready` hangs as in E1. The window is the time between `LV.key = key` and the worklet's `loaded` message, hit when
the song or mix changes while the engine starts.

**E3. Song and preview are created in order; if the second `new Song` throws, the first leaks.** Low. Suspected.
`engine-worklet.js:61`. Wasm heap only; the page recovers by reloading.

**E4. Small, by design.** Mutes are re-sent after `loaded`, so a swap plays a few milliseconds unmuted; a note-off
sent after a swap addresses the new song's channel of the same index; commands sent before the first song is loaded
(`mute`, `tempo`) throw in the worklet and show a transient "engine:" error, then the load's resync sends them again.

**Checked and sound.** `engine-core.js`: the module bytes are copied into the heap and freed (`_free(p)`), the read
buffers are freed with the song, the old song and preview are freed on swap (`free()`, `:63`), heap views are taken
again after every allocation (memory growth safe), the interactive interfaces are fetched by size (16 and 6 entries,
matching 0.8.9), `read()` never asks for more than 4096 frames (the worklet asks for the 128-frame quantum, the node
check for 1024). The metronome, loop and position code in `process()` only touches `this.song` once one is loaded.
The node check renders within 2 LSB of both the vendored 0.8.9 DLL (the owner's machine) and the 0.7.3 library here.

### 5. Correctness elsewhere

**C1. The IT writer overflowed a 16-bit length on dense patterns and long messages.** Medium. Confirmed. **Fixed**
(`9021053`). `itwriter.py:93-115`: the writer packs every cell in full (no last-value compression), so 64 channels
× 150 filled rows is 67 200 bytes and `struct.pack("<HH4x", len(packed), ...)` raised `struct.error`; `:127`: a
message over 65535 bytes the same. `check` said the song was fine. Both are `ValueError`s with the reason now; `check`
still does not report them before the write (test gap T7).

**C2. `swap_sample` writes a `base_note` for any `smpl` unity note, including ones above B-9.** Low. Confirmed. Not
fixed. `api.py:205`: `format_note(125)` is `~~~`, which `_note` rejects. In the app the write is refused now (F1);
the CLI `tryout` still fails to compile such a candidate.
- Suggested fix: use the root only when `0 <= root < 120`.

**C3. YAML 1.1 octal divergence.** Low. Suspected. `song.py:53-58` reads a scalar tagged int that starts with `0` as
decimal (`010` → 10) while `api.from_yaml` (the app's dict of the song, `tryout`, `swap_sample`) reads it as octal 8.
A slot written `010:` compiles as 10 and is slot 8 to the app (after F2's fix it is 10 there too, as `"010".isdigit()`
holds, but a value such as `tempo: 0125` still diverges). Rare; worth one sentence in SONG_FORMAT.md.

**C4. The CLI's `import` caught only `OSError` and `ValueError`.** Low. Covered by P2's fix.

**Checked and sound.** `itwriter.py` against ITTECH.TXT and libopenmpt: header layout and flag bits (old effects
0x10, compatible Gxx 0x20), order padding, offset tables, the 554-byte instrument, envelopes (signed pan/pitch nodes),
sample headers (Cvt = signed, loop flags), the stereo layout (left channel then right: verified by rendering a sample
with 441 Hz left and 2205 Hz right through libopenmpt, `stereo: true` gives 441/2205, `false` mixes to mono);
`build` cross-checks every module with libopenmpt. `notation.py`: parse/format round trips, the volume-column
bases, the ambiguity errors. `song.py`: ranges, duplicate keys, envelope tick ordering, keymap transposition
bounds, `Bxx`/`Cxx`/`Mxx`/`Vxx` checks, the image warning. `patch_it`: the header offsets it pokes (0x31 mix volume,
0x40 pans with the disable bit, 0x80 volumes, sample header +0x11 global volume) are ITTECH's. The in-place editors:
`_put_cell` keeps labels, spacing and comments; implied rows are written out with the block's label width;
`_pattern_block` handles `name: |`, quoted names and `data: |-`; `_span`/`_children` keep comments with their
entries; `_yname` quotes what YAML would misread (`: `, `#`, leading symbols, `true`/`null`, trailing spaces).
`resample.py`: covered by its tests (no imaging up, no folding down, loops seamless). `openmpt.py`: the buffer
passed to libopenmpt is kept alive, strings are freed. Line endings: CRLF files stay CRLF through every write.
`dirty()` guards pattern, song and sample edits and undo (and, after F1, the tryout writes).

## Documentation against the code

1. **README.md** "every ... change ... checked by compiling the whole song before it is written, and undoable": was
   not true for U and WRITE MIX (F1); true on this branch.
2. **GUIDE.md:339** "no note plays a sample more than about seven semitones up": AGENTS.md replaced that rule on
   2026-09-22 (bandwidth times the transposition ratio under about 18 kHz; two octaves for a 4.5 kHz sample). Stale.
3. **GUIDE.md:158** "The order list must be written on one line ... anything else is refused with the reason": a
   block-style list is rewritten on one line, comments lost, not refused (F5).
4. **THIRD_PARTY.md:11** the libopenmpt version is the placeholder `LIBOPENMPT_VERSION`; the vendored DLL reports
   `0.8.9+r25651` (the wasm build `0.8.9+r25652`).
5. **docs/TRACKER-GAPS.md** opens "after program round 6 ... shows the patterns **read-only**" and its tables mark
   the cursor, keyboard entry, undo, selections and more as *missing*, while its closing paragraph says every group is
   built. The tables were never updated; a reader of the tables gets the state of round 6.
6. **SONG_FORMAT.md:61** "Bare `off`, `on`, `yes`, `no` are fine for the enum fields": a bare `yes`/`no` becomes
   `on`/`off`, and no enum field takes `on` (`dct: yes` is an error, only `off` works). Say `off` only.
7. **SONG_FORMAT.md** states no limit for `message` (65535 bytes, IT's field; enforced by the writer now) and none
